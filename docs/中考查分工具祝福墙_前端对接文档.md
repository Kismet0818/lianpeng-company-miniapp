- HTTP 方法：`GET`
- 是否需要 Authorization：否
- 额外请求头：无
- 测试时间：2026-09-10 08:43（Asia/Shanghai）
- 测试环境：本地 `lpsx` 数据库、当前后端代码、独立端口 18080

本次只完成本地代码和接口验证，尚未部署云托管，因此本文不提供尚未生效的线上 URL。

## 2. 请求方式

中考查分工具的全局祝福墙：

```http
GET /api/blessing/list?page=1&size=6
```

学校详情页原有筛选方式继续支持：

```http
GET /api/blessing/list?page=1&size=20&schoolSource=score&schoolId=21
```

`schoolSource` 与 `schoolId` 必须同时提供；只提供其中一个或传入非法值时，返回业务错误。

## 3. 全局查询规则

实际 ORM 条件等价于：

```sql
SELECT id, nickname, avatar, school_source, school_id, school_name, content, create_time
FROM blessing
WHERE status = 1
  AND school_name IS NOT NULL
  AND school_name <> ''
ORDER BY create_time DESC, id DESC
LIMIT 6 OFFSET 0;
```

- 不限制 `school_source`。
- 不追加 `school_id IS NULL`。
- `schoolName` 直接来自 `blessing.school_name`，不联表、不拼接。
- `content` 原样返回，不截断、不改写。
- 相同创建时间用 `id DESC` 保证分页顺序稳定。

数据库字段使用下划线命名，后端 JSON 按项目约定返回驼峰字段。

## 6. 前端解析说明

- 请求工具若已经把统一响应外层的 `data` 解包，页面读取 `result.records`；若使用原始 HTTP 响应，则读取 `response.data.data.records`。
- 接口本身只有一层业务 `data`，不存在额外自定义二次包装。
- `schoolName` 可以直接展示，无需查询或拼接学校表。
- `content` 应由前端按展示需要处理；后端始终返回数据库原文。
- 无有效数据时仍返回 HTTP 200，`data.records=[]`、`total=0`、`pages=0`。
- 业务参数错误结构为 `{"code":400,"msg":"学校参数不正确","data":null}`。
- 系统异常按项目统一异常处理返回，前端应以 `code !== 200` 进入失败提示。
