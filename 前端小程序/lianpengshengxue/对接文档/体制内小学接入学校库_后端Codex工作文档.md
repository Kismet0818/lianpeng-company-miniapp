# 体制内小学接入学校库：后端 Codex 工作文档

> 任务对象：后端 Codex
> 
> 目标：将数据库表 `primary_school` 中的上海市体制内小学接入现有“学校库”，使小学列表卡片、详情页数据能力与当前体制内高中保持一致。前端沿用现有学校库和学校详情页，不重新设计页面。

## 一、任务边界

本次后端工作包括：

1. 阅读现有体制内高中学校库相关代码、实体、Service、Controller、权限配置和接口文档。
2. 阅读并确认 `primary_school` 的真实表结构、字段含义、主键、空值情况和数据量。
3. 为小学提供学校库列表查询接口和单校详情接口，或在现有学校库接口中以兼容方式增加小学数据。
4. 统一返回前端学校卡片和详情页需要的字段，避免前端直接依赖数据库命名。
5. 保证分页、搜索、地区筛选、学校性质筛选和详情查询行为与高中学校库一致。
6. 完成接口测试、数据库数据核对，并输出本文末尾规定的 Markdown 前端对接文档。

不在本次任务范围内：重新设计小程序页面、修改视觉样式、虚构小学数据、修改高中既有业务规则，或把小学记录复制到高中表。

## 二、先行检查要求

开始编码前必须先确认并记录：

- `primary_school` 的完整字段清单和字段类型；
- 主键是否为 `id`，以及主键是否存在重复或空值；
- 当前高中学校库使用的表、接口路径、响应包装、分页组件和权限白名单；
- 当前学校库前端实际读取的字段；
- 小学是否已有图片、简介、地址、办学性质、所属区、住宿等字段；
- 数据库中小学总数，以及按区、办学性质的数量。

如果实际字段与本文示例不同，以数据库真实结构为准，但必须在最终前端对接文档中写出完整映射。

## 三、推荐接口契约

优先新增独立资源接口，避免与其他学校表的 ID 混用：

```http
GET /api/primary-schools
GET /api/primary-schools/{id}
```

列表查询参数至少支持：

| 参数 | 必填 | 说明 |
|---|---|---|
| `page` | 否 | 页码，默认 `1` |
| `size` | 否 | 每页数量，默认与高中一致，并设置合理上限 |
| `district` | 否 | 所属区，精确匹配；需支持上海区名称原值 |
| `keyword` | 否 | 学校名称或简称模糊搜索；若现有高中使用 `name`，需兼容既有约定 |
| `schoolType` | 否 | 公办/民办等办学性质，实际枚举以数据库为准 |

若现有学校库采用统一接口，也可以扩展为 `schoolLevel=primary`，但必须保证小学与高中数据的来源标识、详情查询和 ID 命名清晰，不能仅靠 ID 判断学段。

## 四、响应格式

列表和详情的业务包装应与现有高中接口一致。推荐格式如下：

```json
{
  "code": 200,
  "msg": "成功",
  "data": {
    "records": [
      {
        "id": 1,
        "name": "示例小学",
        "shortName": "示例小学",
        "backgroundImageUrl": null,
        "district": "浦东新区",
        "schoolType": "公办",
        "address": "上海市浦东新区示例路1号",
        "description": "学校简介",
        "schoolLevel": "小学"
      }
    ],
    "total": 1,
    "size": 20,
    "current": 1,
    "pages": 1
  }
}
```

详情接口的 `data` 为单个对象，不是数组。至少统一以下字段：

| 接口字段 | 要求 |
|---|---|
| `id` | `primary_school.id`，仅用于小学资源接口 |
| `name` | 学校全名，必填时不得返回空字符串 |
| `shortName` | 简称，无值返回 `null` |
| `backgroundImageUrl` | 卡片/详情背景图，无图返回 `null` |
| `district` | 所属区 |
| `schoolType` | 办学性质，如公办；保持数据库原始语义 |
| `address` | 学校地址 |
| `description` | 学校简介 |
| `schoolLevel` | 固定返回 `小学` |

如果 `primary_school` 还有电话、官网、办学特色、招生范围、交通、相册等字段，只有确认前端现有详情页会读取时才纳入响应；纳入后必须在对接文档写明字段类型、空值规则和示例。

## 五、数据与实现要求

- 使用只读查询，不修改原始小学数据。
- 查询默认排序必须稳定，建议按数据库主键或学校名称排序，并与分页结合使用。
- 所属区、办学性质等筛选不得通过前端全量猜测；后端应提供真实筛选能力。
- 对名称、简称、地址、简介等文本正确处理 `null`，避免序列化异常。
- 图片 URL 必须返回前端可直接访问的完整地址；如需对象存储签名，说明有效期。
- 不能把 `primary_school.id` 与 `school`、高中、初中等其他表 ID 合并成全局 ID。
- 如系统存在 `schoolSource`/学段标识，统一返回 `schoolSource: "primary"`、`schoolLevel: "小学"`；具体命名必须在前端文档中固定下来。
- 列表和详情接口的鉴权、公开白名单、错误码规则与现有学校库/高中接口保持一致，并明确是否需要 JWT。
- 详情不存在时返回稳定的业务错误，例如 `code: 400`、`msg: "小学不存在"`，不得返回 HTTP 200 加空对象掩盖错误。

## 六、验收要求

后端完成后至少验证：

1. 不登录或按现有规则携带 Token 请求小学列表，响应包装正确。
2. 默认分页、最大分页、空关键词、名称关键词、地区筛选、办学性质筛选均可用。
3. 列表中每条记录点击对应 `id` 均能返回正确小学详情。
4. 随机抽取每个上海行政区至少一所小学，核对名称、区、性质与数据库一致。
5. 空字段、特殊字符、超长简介、无图片记录不会导致接口 500。
6. 不存在的 ID 返回约定错误；高中原有列表和详情回归测试不受影响。
7. 使用实际 HTTP 请求或自动化测试记录请求参数、响应状态、业务码和返回条数。

## 七、必须交付的前端对接文档

任务结束时，必须在仓库 `对接文档/` 目录新增一个 Markdown 文件，文件名建议：

```text
体制内小学接口_前端对接文档_YYYYMMDD.md
```

该文件必须包含：

- 实际可用的列表、详情接口路径和 HTTP 方法；
- 完整查询参数表、默认值、最大值和编码规则；
- 成功响应 JSON 示例，以及列表字段和详情字段逐项说明；
- 数据库字段到接口字段的实际映射；
- `schoolSource`、`schoolLevel`、`id` 的最终约定，并明确 ID 不可跨表复用；
- 鉴权要求、公开白名单和部署/重启要求；
- 空数据、无图片、无简介、无效 ID、401/403/429/500 的响应及前端处理建议；
- 至少 3 条可直接复制执行的联调 curl 示例；
- 已完成的测试记录：数据总量、至少两个区的返回数量、详情抽样结果；
- 前端需要改动的页面或字段（若无需改接口之外的内容，也要明确写出）；
- 未完成事项、已知限制和后续建议。

最终回复不得只写“接口已完成”。必须同时给出该 Markdown 文件的路径，并简述测试结果。若因数据库结构、部署权限或图片服务无法完成，必须在文档中明确标注“阻塞项”，不得用模拟响应冒充完成。
