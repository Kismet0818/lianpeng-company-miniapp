# 体制内幼儿园接入学校库：后端 Codex 工作文档

> 任务对象：后端 Codex
>
> 目标：将数据库中已有的上海市体制内幼儿园数据接入现有“学校库”，使幼儿园能够被前端按学校库资源正常查询、展示、查看详情，并与小学、初中、高中保持一致的接口包装、鉴权、来源标识和数据质量标准。

## 一、任务范围

本次任务包括：

1. 阅读现有学校库以及小学、初中、高中相关的实体、Service、Controller、鉴权白名单、统一响应和前端对接文档。
2. 确认幼儿园真实数据表、字段、主键、数据量、空值情况、地区分布和办园性质分布。
3. 提供幼儿园列表查询接口和单园详情接口；如扩展统一学校库接口，必须保留清晰的学段和来源标识。
4. 将数据库字段映射为稳定的前端接口字段，前端不得直接依赖数据库字段命名。
5. 完成分页、关键词、地区、办园性质等实际可用的筛选能力，并完成真实 HTTP 验收。
6. 任务结束时，在 `对接文档/` 目录新增本文规定的“前端 Markdown 对接文档”。

不在范围内：虚构或批量改写幼儿园原始资料、把幼儿园记录复制到小学/初中/高中表、修改既有学校学段规则、重新设计前端页面视觉样式。

## 二、开始编码前必须核查

必须先通过代码和数据库确认并记录：

- 幼儿园实际表名、完整字段清单、字段类型、主键及主键重复/空值情况；
- 当前幼儿园总数，以及按上海行政区、办园性质的数量；
- 当前学校库和小学接口使用的响应包装、分页字段、排序、错误码和鉴权规则；
- 是否已有幼儿园 Controller、接口、实体或前端页面，避免重复实现或破坏旧接口；
- 数据中真实存在的字段：园所全名、简称、图片、区、地址、办园性质、等级、收费、住宿、简介、官网、联系电话等；
- 数据库中的幼儿园是否全部属于“体制内”。若无法确认，必须在前端交接文档中说明筛选口径和阻塞项。

不得根据字段名猜测数据含义；实际数据库结构与本文示例不一致时，以真实结构为准，并在最终前端文档中给出完整映射。

## 三、推荐接口契约

优先使用独立资源接口，避免幼儿园与其他学段共用 ID 空间：

```http
GET /api/kindergartens
GET /api/kindergartens/{id}
```

如果项目已有统一学校接口，也可以采用 `schoolLevel=kindergarten` 或等价方案，但必须满足：

- 返回 `schoolSource: "kindergarten"` 和 `schoolLevel: "幼儿园"`；
- 详情查询不能仅凭数字 ID 判断学段；
- 幼儿园原表主键不得与其他学校表 ID 合并或自动复用；
- 兼容旧接口时不得改变小学、初中、高中现有返回语义。

列表至少支持以下参数（若数据不具备某项筛选，必须明确说明，不得伪造筛选）：

| 参数 | 必填 | 说明 |
|---|---|---|
| `page` | 否 | 默认 `1`，小于 1 的处理规则须固定并记录 |
| `size` | 否 | 默认值与现有学校库一致，设置最大值并记录 |
| `district` | 否 | 所属区精确匹配，支持数据库实际区名 |
| `keyword` | 否 | 对幼儿园全名、简称模糊搜索；如兼容 `name`，说明优先级 |
| `schoolType` / `kindergartenType` | 否 | 仅选择一个最终字段名，按真实办园性质精确匹配 |

默认排序必须稳定，建议使用“区 + 园名 + 主键”排序；分页查询不能依赖不稳定的无序结果。

## 四、响应要求

列表和详情必须沿用现有接口包装，推荐如下：

```json
{
  "code": 200,
  "msg": "成功",
  "data": {
    "records": [
      {
        "id": 1,
        "name": "示例幼儿园",
        "shortName": null,
        "backgroundImageUrl": null,
        "district": "浦东新区",
        "schoolType": "公办",
        "address": "上海市浦东新区示例路1号",
        "description": null,
        "schoolSource": "kindergarten",
        "schoolLevel": "幼儿园"
      }
    ],
    "total": 1,
    "size": 20,
    "current": 1,
    "pages": 1
  }
}
```

详情接口的 `data` 必须是单个对象，不是数组。至少统一以下字段；没有真实数据时返回 `null`，不要返回虚假文本：

| 接口字段 | 要求 |
|---|---|
| `id` | 幼儿园原表主键，只在幼儿园资源范围内有效 |
| `name` | 园所全名；真实必填时不得返回空字符串 |
| `shortName` | 简称，无值返回 `null` |
| `backgroundImageUrl` | 前端可直接访问的完整图片 URL，无图返回 `null` |
| `district` | 所属区，保留数据库真实行政区名称 |
| `schoolType` | 公办/民办/其他真实办园性质；最终枚举须记录 |
| `address` | 地址，无值返回 `null` |
| `description` | 简介，无值返回 `null` |
| `schoolSource` | 固定为 `kindergarten` |
| `schoolLevel` | 固定为 `幼儿园` |

如纳入等级、收费、住宿、联系电话、官网、办园特色等字段，必须只纳入真实存在且前端有使用价值的字段，并在前端 Markdown 中写清类型、空值规则和示例。

## 五、实现与数据要求

- 使用只读查询，不修改幼儿园原始资料；如必须补充来源标识，采用代码层固定值或安全的映射，不覆盖原始数据。
- 列表、详情、筛选、排序和分页行为与现有学校库保持一致。
- 正确处理 `null`、空字符串、特殊字符和超长简介；不能因单条脏数据导致整个列表 500。
- 图片必须返回前端可访问的完整 URL；若使用签名 URL，写明有效期和前端刷新策略。
- 鉴权、公开白名单、限流、错误码和响应包装必须与现有学校库约定一致。
- 不存在的 ID 返回稳定错误，例如 `code=400`、`msg="幼儿园不存在"`、`data=null`；不得用 HTTP 200 加空对象掩盖错误。
- 如现有前端收藏、评价、祝福墙、浏览行为、学校比对或埋点按 `schoolSource` 分流，检查并补齐 `kindergarten` 解析；不得只按数字 ID 猜测学段。

## 六、验收要求

必须使用真实数据库和真实 HTTP 请求验证：

1. 默认分页、最大分页、空关键词、名称关键词、地区筛选、办园性质筛选可用；
2. 列表每条记录的 `id` 均可请求到对应详情；
3. 至少抽取上海不同区域的幼儿园，核对名称、区、办园性质与数据库一致；
4. 空图片、空简介、特殊字符、超长文本不会导致 500；
5. 不存在 ID、越界分页、未授权请求的响应符合约定；
6. 小学、初中、高中原有接口回归不受影响；
7. 记录数据总量、区分布、办园性质分布、典型列表响应、详情抽样结果和测试命令；
8. 若因表结构、数据质量、部署权限或图片服务无法完成，必须标注“阻塞项”，不得用模拟响应冒充完成。

## 七、任务结束时必须交付前端 Markdown 对接文档

后端任务结束时，必须在仓库 `对接文档/` 下新增文件，建议命名：

```text
体制内幼儿园接口_前端对接文档_YYYYMMDD.md
```

该文件必须包含：

- 实际可用的列表、详情接口路径和 HTTP 方法；
- 所有查询参数、默认值、最大值、枚举值和 URL 编码规则；
- 成功列表/详情 JSON 示例，以及字段逐项说明；
- 幼儿园真实数据库字段到接口字段的完整映射；
- `id`、`schoolSource="kindergarten"`、`schoolLevel="幼儿园"` 的最终约定，并明确不得跨表复用 ID；
- 鉴权、公开白名单、限流、部署/重启要求；
- 空数据、无图片、无简介、无效 ID、401/403/429/500 的响应和前端处理建议；
- 至少 3 条可直接复制执行的联调 curl 示例；
- 真实测试记录：数据总量、至少两个区的返回数量、详情抽样结果、回归测试结果；
- 前端需要修改的页面、请求参数、字段、跳转参数、缓存/收藏/评价/埋点影响；若无需额外修改，也必须明确写出；
- 未完成事项、已知限制和阻塞项。

最终回复必须同时给出该前端 Markdown 文件的实际路径，并简述真实测试结果。只回复“接口已完成”视为未完成交付。
